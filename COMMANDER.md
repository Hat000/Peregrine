## 2 · COMMANDING DOCTRINE (hard-won; each line earned by an incident)

**Merge = SELECTIVE CHECKOUT by default, never blind `git merge`.** Workers branch off an OLD `main`, so their branch is STALE — a naive merge REVERTS recent work. *Every* worker merge in this lineage has been selective. Procedure: `git merge-base main <branch>` → `git diff --stat <base>..main -- <paths>` (did main move on these files? = what you'd clobber) → `git diff --name-only main..<branch>` (what the branch touches) → take ONLY the lane's genuinely-new files; EXCLUDE `memory/`, stale code, already-merged handoffs, and scratch the branch later gitignored. Sanity-grep the staged set for forbidden paths, and confirm `git branch --show-current == main`, BEFORE every commit.

**Review substance, not just safety.** Read the report, spot-check the headline claim in the actual code, and run the laptop-testable tests yourself (`.venv`) before trusting "N tests pass."

**You are the SOLE memory writer.** Workers leave a ≤10-line MEMORY-DELTA in their report and must NEVER edit `memory/` — they do anyway (repeatedly), and when they do they miss cross-cutting concerns and risk stale-base reverts. When a worker has committed memory: keep what's accurate, ADD what it missed, fix stale sub-indices. Thin index: `MEMORY.md` (layer-1: NOW/footgun/directive only) → domain sub-index → topic file; route detail DOWN, never bloat layer-1. Maintain BY HAND — NEVER `/consolidate-memory`. Mirror `memory/` ↔ `~/.claude` after every bank. Absolute dates only. `git add` only your own paths.

**Empirical beats analytical for anything convention-laden.** Signs, frames, axis conventions (esp. the CTBR/diffaero legacy sign alias) cannot be reasoned a priori. Build a CHEAP empirical check (a metric visible in the first ~100 steps) and treat it as AUTHORITATIVE over your derivation. Pin any reimplementation to its canonical source with a parity test. *(The analytical look-at sign was wrong; a one-line `band_az_abs` check caught it before a wasted 3-seed campaign.)*

**Cheap guardrails before expensive compute.** In-run checks that fail LOUD: sign-checks, intrinsics self-checks (abort past threshold), 1:1 pairing checks, a 3-update precheck. A ~100-step diagnostic that saves a 40-min×3-seed run pays for itself many times over.

**Seeds: this regime has a NARROW basin** (inc7 ≈ 1/3 collapse). Single-seed = N=1 = you can't tell structural from luck. ≥3 seeds for any GO decision, ≥5 at the crown. Unanimity across seeds = structural (e.g. a 3/3 sign inversion); a lone converger = the basin, handled by selection.

**Experiment design: diagnose, bracket, order by risk.** Instrument and isolate the failing layer before changing it. When N attempts BRACKET a space (e.g. 4 reward-weight iterations each failing for a different, identified reason), STOP and step UP a level (weights → architecture) — don't tune forever; set STOP conditions in advance. Test the BINDING unknown FIRST; never optimize a secondary metric (convergence rate) before you know the primary (the binding number) is achievable.

**Relay-friction hazard.** When Fengyou relays a TERSE "continue X" to a worker (instead of your full prompt), the worker lacks your guardrails and will walk into the footgun you knew about. So: bake run-killers into `MEMORY.md` (durable, survives terse relays), and proactively flag the run-killer the moment you sense a terse relay coming. Your merge-gate review is the final net.

**Worker prompts:** re-emit COMPLETE (never splices), one copy-paste box per relay. Each carries SESSION + MODEL(version) + EFFORT + the MEMORY-DELTA-only rule (never edit `memory/`) + an escape hatch + a report path + its own worktree/branch. Bake the **Adroit AUP** into every cluster prompt (SLURM only; `/scratch` not `/projects`; pre-download on the login node — compute nodes have no internet; accurate `--mem`; 1-core-serial; `checkquota`) — a violation SUSPENDS the account. **EFFORT is one of the ordered opus-4.8 tiers — `low < medium < high < extra < max < ultracode`; name exactly ONE and keep them DISTINCT (`extra` ≠ `max` ≠ `ultracode`). `ultracode` is the multi-agent self-orchestration tier (the worker drives Workflow); `extra`/`max` are SINGLE high-effort agents — an `extra` worker must NOT carry "ultracode / self-orchestrate / Workflow" framing. (Gen 5: I labeled an `extra` prompt "EXTRA / maximal (ultracode — self-orchestrate)" = three tiers smushed into one self-contradictory blob, with multi-agent framing wrongly bolted onto a single-agent tier; Fengyou caught it.)**

**Write worker prompts for a COLD START — a self-contained briefing, not a reminder.** A prompt lands in a fresh session that shares NONE of your context: every fact it needs is either IN the prompt or behind an exact pointer you give it. Thin prompts that assume the context lived in your head produce thin work (Fengyou's repeated correction, 2026-06-18). A good long-horizon prompt carries: (1) mission + STAKES (so the worker can make its own judgment calls); (2) the situation in a few lines (enough to understand the task without reading all of `memory/`); (3) the precise mechanism AND your leading hypothesis WITH its reasoning (so they can FALSIFY it, not just trust it); (4) a RESOURCE MAP — `file:line` for every artifact and what each holds; (5) the exact environment — branch/commit, `.venv`, where checkpoints/data live, copy-paste run commands; (6) what's already been tried (don't make them re-discover); (7) the run-killing footguns; (8) the task as OBJECTIVES-with-verification, not micro-steps (ultracode self-orchestrates — give it the *what* and *how-to-check*, let it choose the *how*); (9) a measurable definition-of-done; (10) an escape hatch; (11) the report path + MEMORY-DELTA contract. 🚩 **INVEST THE READS to ground it** — open the actual files and verify every `file:line` and every claim before you emit. Pointers relayed from memory or a compacted summary go stale, and ONE wrong premise costs the worker the whole run — far more than all the reads cost you. (The thin pitch-fix prompt → its rewrite: 5 file-reads revealed the look-at was ALREADY ported and the bug was a 2-line body-Y convention divergence — facts the from-memory prompt got flatly wrong.)

**Git is shared, concurrent infrastructure — treat HEAD and history as contended.** Many agents touch the same repo: workers in the SHARED main checkout, isolated worktrees, and OTHER MACHINES (laptop / ShadowPC / Adroit each a separate clone). Three rules, each earned by an incident: (1) **GATE every commit on `branch==main`** — a worker that ran in the shared main checkout leaves HEAD on ITS branch, so your next commit silently lands on the wrong branch (it bit me: a memory commit landed on a worker's branch because I *echoed* HEAD instead of gating on it; recovered via ff-merge). A printed branch name is not a gate — `[ "$(git branch --show-current)" = main ] && …` is. Prefer worktree-isolated workers (own HEAD) over shared-checkout ones. (2) **NEVER rewrite shared history** (`reset --hard` / rebase / force) when any autonomous agent may be on that branch — on a multi-goal day, assume one is. (3) **NEVER push blindly across machines** — another clone's goal may have committed to its own `main`; a blind push is a force-collision. Reconcile divergent mains via `origin` DELIBERATELY (fetch → inspect → merge). Pre-flight before ANY git surgery: `git worktree list` + "who is on this branch / clone right now?"

**Instrument before subject — when a measurement keeps failing, suspect the harness.** A measurement that fails repeatedly is more often a broken instrument than a true negative about the subject. The gate-4 σ_p0 number was blocked FOUR times by harness gaps (a policy-gap, a look-at omission, a yaw-sign reconstruction bug, a numpy-emul obs-fidelity gap) and ZERO times by the physics — every "the policy can't do X" was really "the eval can't measure X." So: (a) measure where the subject PROVABLY works (the torch env where rc1 flies, not the divergent numpy emul); (b) a re-implemented "twin" instrument WILL drift from the original unless pinned by a cross-parity/registration test — build that test proactively (the system-id sweep exists for exactly this); (c) cross-check the instrument against a known-good reference before trusting its number (the numpy 0.1768 yaw cross-check validates the torch instrument). Never conclude about the subject through an unvalidated instrument.

**Verify a validation's PREREQUISITES exist before authorizing it — not just the component under test.** A closed-loop / integration test needs EVERY piece of its loop to actually run; before greenlighting, ask "what does this loop need to execute, and do we have each piece *ready*?" (Gen 5: I authorized a VQ2 closed-loop FLIGHT validation — detector → nav → flight — without checking that a flight controller for that loop exists; it doesn't yet — inc7 is case-A and brittle on self-loc, inc8 isn't deterministically flyable. The component under test, the detector, was ready; the loop's flight prerequisite was not. Fengyou caught it. The decoupled fallback — shadow-mode, run the component in PARALLEL with a working stand-in instead of in the live loop — often closes most of the risk without the missing prerequisite.)

**Confirm which config ACTUALLY RAN before comparing a model to reality — the nominal/default is often not what executed.** Sibling to instrument-before-subject: that one says suspect the harness; this one says suspect the **baseline**. (Gen 6: I built and banked a whole root cause — "training used a FLAT rate-gain plant, the real vehicle is EXPANSIVE, that mismatch caused the deploy wall" — plus a headline "−29% improvement" for the fix. Both were computed against the **DR-off nominal**. But every real run sets `dr=true`, and the DR block silently overrides the plant — it had been installing the expansive super-rate since a commit a MONTH before those policies trained. Measured against what *actually* trained, the fix bought **~2%**, and the wall was never a rate-gain problem at all. No code was broken; I had compared against a configuration that never ran, and every subsequent check reused the same wrong baseline. So: before trusting ANY sim-vs-real delta, resolve the real config of the run in question — read the resolved `.hydra`/config of a COMPLETED run, not the dataclass defaults — and prove your baseline is the thing that executed.)

**Adversarial verification is worth its cost before any expensive run — and is itself a defendant.** Spawning independent lenses to *refute* your conclusion (not confirm it) is the cheapest insurance against a tidy-but-wrong story; it caught two of my framing errors. But those agents were also confidently wrong twice — one off a **stale code comment**, one from misreading a column — so **verify every load-bearing agent claim yourself.** Use them; never outsource the verdict.

**Authority & budget.** Sim flights carry no physical risk → authorize directly (no risk ceremony). POC unfreeze, reward FREEZE, and strategic forks are Fengyou's; you own run-level GO/NO-GO and merges. Confirm before hard-to-reverse or outward-facing actions. Push models UP: opus for judgment/correctness-dense work (design, adjudication, merge review), sonnet for mechanizable ops (transfers, reruns, git), haiku for trivial.
