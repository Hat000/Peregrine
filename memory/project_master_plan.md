## Edge-compute budget (2026-05-29) — ~100 TOPS onboard reframes the perception/policy ambition
FAQ-confirmed: the onboard edge device is **~100 TOPS** (Jetson-Orin-class NPU). **TOPS = NEURAL-NET inference capacity** (INT8 tensor ops); classical work (KF, PnP, min-snap QP, reactive LOS) consumes ~0 TOPS. Our stack today has ONE small NN (YOLO-pose) ⇒ we use a few % of the budget. So "use the compute" = **move workload onto neural nets that improve runs**, within the latency budget — NOT inflate the classical bits.

**Discipline (so this doesn't go gratuitous):**
- **TOPS ≠ latency.** A net that eats 40 ms hurts closed-loop control more than a small one at 5 ms helps. Spend TOPS where latency is tolerable (perception at the ~33 ms frame budget; offline/parallel rollouts); keep the CONTROL path lean. Size models to the <~50 ms end-to-end budget, not just the TOPS budget.
- Heavier learned components are UPGRADES behind the frozen contracts; the model-based floor stays the safety net. Bank the VQ1 floor first.
- Compute is necessary-not-sufficient: the bottleneck shifts to DATA + training (Adroit) + the sim-to-sim gap, not FLOPs.
- **Applicability:** ~100 TOPS is the ONBOARD/deployment envelope (physical qualifier Sept + finals); the VIRTUAL quals run on cloud GPU. It (a) kills the "be frugal" mindset — use heavier learned models in VQ1/VQ2 too, and (b) argues for building the deployment-target heavy-NN stack NOW so VQ→physical needs no rearchitecting (walking-skeleton, extended to compute). VERIFY whether the virtual sim enforces a compute/latency cap; design to ~100 TOPS regardless.

**VQ1 — buys VALIDITY/reliability (don't break the chain):**
- Size the detector UP (YOLO11-m/l, higher input res, a temporal/multi-frame head) ⇒ fewer missed/garbage detections at range + under motion blur (the riskiest vision cases; a missed/garbage detection = dropped-loop/missed-gate = invalid). Cheap insurance the budget now makes ~free.
- A small learned detection-confidence / corner-outlier filter to gate bad PnP inputs.

**VQ2 — buys SPEED/RANK (the budget is the differentiator here):**
- **Deploy a learned racing POLICY (RL) — the budget makes onboard NN-policy inference essentially free**, a concrete compute justification for the RL-on-Elodin-Adroit stretch. THE differentiator. **TRAIN-IT HARD REQUIREMENT (2026-05-31): inject a MEASURED perception noise/latency/dropout model (from first-contact recordings) into the policy's observations + asymmetric actor-critic (privileged critic sees truth, actor sees noisy perception-state). A policy trained on PERFECT state crashes on real YOLO-pose→PnP→KF at speed (the user's catch); perception fidelity = the RL speed CEILING (= "estimation = a speed cap w/ safety valve"). Raw-pixels vision-in-loop REJECTED (reintroduces the appearance gap; kills the non-rendered parallel dynamics-sim; SWIFT avoided it). Middle path: gate-relative visual obs (corner px/bearing) to the policy. See [[project-tooling-recommendations-eval]].**
- **GPU/parallel sample-based MPC (MPPI)** — thousands of trajectory rollouts per control tick, real-time on this hardware ⇒ near-time-optimal aggressive lines robust to model error (embarrassingly parallel; loves TOPS). Classical complement/alternative to RL.
- **Learned monocular DEPTH** (Depth-Anything / Metric3D-class @30 Hz, now affordable) ⇒ REOPENS the "no monocular depth ⇒ don't map obstacles" rejection (review-validation #11): a 3D map (gates + obstacles + free space) enables a globally-optimal collision-free line + safe corner-cutting, not just a gate corridor. **PREFERRED obstacle-mapping route (2026-05-29, user): OFFLINE multi-view triangulation, NOT real-time depth — run a (generic/class-agnostic/fine-tuned) detector + ByteTrack over a RECORDING, take a tracked obstacle's stable pixel across 2+ frames, build P1/P2 from the logged `NavState` poses (`frames.py`) and `cv2.triangulatePoints` → metric NED point → drop an infinite vertical cylinder (X,Y) into the map → regen the min-snap line for the NEXT attempt. Determinism makes this STRICTLY BETTER than real-time monocular depth here: metric (no scale ambiguity), ~0 real-time cost, reuses recorder+NavState+frames+map. Given attitude KILLS the optical-flow rotational-FOE problem (reconstruct rotation from logged pose, don't estimate it). CAVEATS to engineer around: (1) translational-parallax degeneracy REMAINS for obstacles ~along the velocity vector (dead-ahead triangulates poorly even with perfect pose) → pick best-lateral-parallax / multi-view pairs, not a fixed A/B; (2) accuracy ∝ RELATIVE-pose accuracy → triangulate only between confident gate fixes (low KF cov) + propagate pose cov into the cylinder radius (0.3 m drift on a ~1 m baseline wrecks it); (3) bbox-center is NOT a fixed 3D point (slides over the surface) → triangulate a stable feature (floor-contact base) + safety radius; vertical-cylinder model also misses horizontal bars; (4) 'generic YOLO suffices' is optimistic — truss/net/boundary aren't COCO ⇒ likely need class-agnostic or fine-tuned obstacle detection (flywheel). STILL CONTINGENT (review #11): build when a recording shows the gate corridor ISN'T collision-free, not speculatively — but this is the chosen architecture + cheap to stand up. Lightweight is NOT the axis (it's OFFLINE ⇒ compute/latency free); spend the 100 TOPS on the REAL-TIME detection path. Learned depth = real-time backstop for UNmapped obstacles only.**
- **Multi-frame / temporal perception** for robust high-speed detection (motion blur is the hard case at race speed).

**Unchanged (don't inflate):** estimation is small (attitude GIVEN ⇒ only x,y is vision-only) — keep the linear KF; heavy VIO is low marginal value. Classical PnP/min-snap are fine for the floor (they don't touch the TOPS budget anyway).

## Effort prioritization (2026-05-28) — where the win actually is
Frame "core challenge" two ways: what makes a run VALID (counts at all) vs what RANKS you among valid runs (time). The stack is a chain vision→estimation→planning→control→(sim stabilizer): the chain must not BREAK (any broken link = invalid/crash), and among unbroken chains TIME is set almost entirely by the PLANNING link.

- **VQ1 core = reliability / engineering robustness**, not any algorithm. Don't miss a gate, don't crash, don't drop the loop. Vision is NOT the bottleneck here. Bank it with the simplest floor.
- **VQ2 core = the racing line + speed profile** (planning / trajectory-opt / RL policy), flown near the dynamic limits without going invalid. THE differentiator; where ~unlimited attempts + determinism pay off (iterate the line on the real sim). Fits the user's RL strength.
- **Vision = price-of-entry / threshold**, not the prize. Gate detection is highly solved; the course is DETERMINISTIC WITHIN a round (same gates+lighting every run) ⇒ no cross-domain problem inside a round. **BUT (correction 2026-05-29): VQ1→VQ2 IS a domain shift — VQ1 clean/desaturated/aids-on, VQ2 photoreal/cluttered/aids-off. So "overfit to the course" applies to GEOMETRY (layout/poses/line), NOT APPEARANCE: fine-tuning the detector on clean VQ1 frames would COLLAPSE the synthetic-DR robustness right before the ranked VQ2 round. PRESERVE DR / train in chaos (albumentations); the flywheel donates hard real GEOMETRY with photometrics randomized away; only VQ2 frames may shape VQ2 appearance priors (see the detector component).** Need: general-enough for attempt-1 on an unseen track (synthetic domain-randomization) → overfit GEOMETRY/the line to the course via the flywheel while keeping appearance randomized. Threshold character: below it = invalid, above it = wasted effort. (Hardest vision sub-problems are motion-blur / clipped-gate-at-transit + long-range pose — multi-frame fusion, not "more lighting.")
- **Estimation = a speed CAP with a safety valve.** Blind-segment drift forces you slower, but you can always slow to stay valid. Simple KF + baro/mag suffices.
- **Control = mostly handed to you** by the sim's Betaflight-style stabilizer. System-ID once; generate good setpoints. Low marginal difficulty.

**Adroit allocation:** HEAVY → RL racing policy on the Elodin surrogate (the differentiator; fits the user's strength). BOUNDED → detector (synthetic pre-train + flywheel fine-tune to the actual course; a few runs, not weeks). NOT → a lighting/scenario robustness campaign.

**Discipline:** build vision to "good enough," then MEASURE on real VQ2 frames whether detection breaks the chain; escalate vision only if measured to be the bottleneck (default expectation: planning is where VQ2 rank is won). Bank VQ1 with the floor before any VQ2 polish.

## Gate ordering (resolved design)
A racing line needs an ORDERED waypoint list; detections are unordered. Order comes from one of: (A) sim provides an ordered coarse gate list → free; (B) sim provides unordered positions → greedy "nearest unvisited gate ahead along the through-direction" (constrained TSP, easy); (C) sim provides nothing → discover by traversal (fly through the gate ahead, steer to the next visible, never re-target a passed gate; pass-order = order). You never need GLOBAL order to fly — only "which gate is next," and courses put the next gate ahead. Record a clean ordered traversal once (attempts permitting) and define order once. VQ1≠VQ2 ⇒ solve per course. Control tracks the next gate RELATIVE to the drone; the global map is only for ordering + trajectory.

## Guiding principles
- VQ1 floor works with minimal parts; VQ2 ambitions slot into pre-cut interfaces. A slow VALID finish beats a fast invalid one (invalid scores nothing).
- **Exploit determinism (per track):** geometry + physics are identical every run on a given track ⇒ overfitting a mapped line is valid and noise-free system-ID is possible. NOT a generalization problem within a track. (But the track is NOT known in advance, and VQ1≠VQ2 — so map, then race.)
- Azure spend is NOT a constraint: parallel sim instances, bigger VMs, optimize directly on the real sim. Only avoid idle waste. Adroit = FREE supervised detector training.
- Ground decisions in VERIFIED rules; track UNKNOWNS explicitly; resolve them at first sim contact.
- Vision stays in the loop during timed runs (re-anchors position; keeps the run legitimate).

## Architecture
Two modes over shared plumbing:
- EXPLORE: reactive fly-next-visible-gate; record the ordered gate map + data (frames + telemetry).
- RACE: track the pre-computed line through the ordered map; vision corrects drift + confirms gates.
