A third-party list of ~22 drone-racing tools was triaged against the ACTUAL code + strategy (same discipline as [[project-red-team-pass-2]]/[[project-red-team-pass-3]]). **The lens that decides most of it:** the list's center of mass is *real-hardware FPV racing* (Jetson+STM32 you flash, fisheye cams, motor-RPM control @500–1000 Hz, real aero, sim-to-**real** transfer — the DCL/UZH-RPG/TU-Delft world). Our near-term reality is a **virtual qualifier**: a MAVLink-**setpoint** sim (lowest surface = CTBR/`BODY_RATE`, <100 Hz, into a black-box stabilizer — confirmed [contracts.py](src/racer/contracts.py)), **attitude GIVEN**, **pinhole** camera (no distortion), inference on **cloud GPU**, no physical drone until Sept. The list sits ~one phase ahead of + one abstraction-level below us. Keepers are the ones that survive that reframing. Sequencing: **all post-VQ1/VQ2** (user: "everything else comes after vq2 drops"); only TOPP-RA was spiked now.

**ADOPTED / QUEUED:**
- **TOPP-RA — SPIKED 2026-05-31.** The *speed* rung of the planner ladder (geometry = min-snap line; timing = this), behind the same `Setpoint` seam. Built pure-numpy `src/racer/speed_profile.py` (`time_optimal_profile` → `Trajectory.setpoint_at`; forward/backward integration w/ the curvature-coupled accel budget `a_tan=sqrt(a_max²−(κv²)²)`; 8 tests, 184 total green). **`toppra` itself does NOT build on Windows+py3.13** (Cython/C++, missing Windows SDK `io.h` — same build-pain class as acados); added as a `[planning]` extra gated `platform_system != 'Windows'` (installs on the Linux sim box/Adroit as a drop-in robustness upgrade behind the identical API). Better than the naive α time-scaling we'd planned; a classical time-optimal baseline AND a reference/initialization line for the RL policy. Feed it the **system-ID'd achievable** v/a limits (R2/`innerloop_step`), not theoretical.
- **Actuator / dynamics randomization** (motor τ ±30%, thrust coeff ±20%, + latency) → fold into the RL sim-to-sim spec. Sharpens our "domain randomization + residual step": randomize the *plant/stabilizer response* (gain/delay/τ/saturation around the system-ID'd nominal), not just lighting/wind — dynamics mismatch is what kills transfer.
- **State-based adaptive cropping** → DEFERRED VQ2 long-range perception lever. Use the KF prediction to crop+upscale the predicted gate ROI → run a heavier model on the pixels that matter (helps tiny-gate-at-range, our hard case). Correctly out of the VQ1 floor: it couples detect→estimator (bad prediction → missed crop), which the walking-skeleton forbids. NB the author imagines 1080p/4K; we're 640×360 so the *latency* win is small, the *long-range resolution* win stands. Escalate only if measured to break the chain.
- **Apache TVM / NVIDIA TAO** → PHYSICAL-round (Sept+) edge-deploy toolchain (INT8/prune for onboard Orin). Premature for virtual quals (cloud GPU, plain PyTorch/ultralytics). TAO = more turnkey if onboard = Orin-class.

**KEY NEW INSIGHT — perception noise model is a HARD requirement for the RL policy (the highest-leverage output of this session; user surfaced it):** state-based RL trained on PERFECT ground-truth state, then deployed on real noisy/laggy/dropping YOLO-pose→PnP→KF, flies at the dynamic limits assuming perfect info and **crashes** on the first motion-blur miss / lagged long-range fix at speed. Fix (what SWIFT actually did): **measure** our perception error from first-contact recordings (detection rate vs range/speed/blur, PnP cov vs range, latency, transit dropout / the "perceptual desert") and **inject that noise+latency+dropout model into the policy's observations during training**; use **asymmetric actor-critic** (privileged critic sees truth, actor sees the noisy perception-state). Consequence: perception fidelity becomes the RL **speed ceiling** (can't fly faster than it can localize) = our "estimation = a speed cap with a safety valve" — fails slower, not crashier. **Raw-pixels vision-in-loop RL = REJECTED** (reintroduces the VQ1→VQ2 appearance gap we isolate via "overfit geometry, randomize appearance"; forces photoreal rendering per env → kills the massive non-rendered dynamics-sim parallelism; SWIFT avoided it). **Middle path noted:** feed the policy compact *gate-relative* visual observations (corner pixels / bearing to next gate) alongside/instead of fused world state — FPV-pilot-aligned, robust to localization/map error; consider once the noise model exists.

**PARKED AS FALLBACK (retain; do not adopt now) — user: "good to hang on to these":**
- **VIO family — VINS-Fusion, OpenVINS, LARVIO, VID-Fusion.** We don't run VIO by design (attitude GIVEN, baro→z, mag→yaw; only x,y is vision-only; perceptual-desert coast de-risked <0.3 m/1 s in [state_estimator.py](src/racer/state_estimator.py)). **RETAIN as the escalation IF first-contact shows attitude missing / biased / low-quality, or we otherwise want camera odometry through the desert.** Same data-driven trigger as the deferred ESKF-bias-state. VID-Fusion's *external-force* estimation → inspiration for a disturbance/residual term in the KF/controller (the placeholder thrust scale + drag at speed) — a separate, smaller idea, not the VIO.

**INSPIRATION ONLY (concept yes, tool no):**
- **G&CNets (TU Delft):** output motor RPM @500 Hz — **unusable** (our floor is CTBR via SET_ATTITUDE_TARGET, <100 Hz, into the black-box stabilizer; we never command motors). But the *tiny-dense state→action net* IS our RL policy architecture (SWIFT). Take the architecture, not the interface.
- **TinyMPC:** whole pitch is run-MPC-on-the-flight-controller-STM32 — we have no FC to flash (the sim is the vehicle, over UDP). Concept = a lean tracker; acados covers it if we go classical.
- **Gate-Fused EKF** (online gate-SLAM in the state vector): determinism lets us **map gates offline** (average many sightings → precise fixed map) — strictly simpler/better than estimating gate poses live. Inspiration → the mapper (bundle-adjustment-flavored gate refinement) + propagate residual gate-position uncertainty into the localizer covariance.
- **LMPC / Frenet-singularity note (TUM):** (a) the Frenet-frame high-curvature singularity is a real failure mode to remember *if* we build MPCC; (b) LMPC's iterate-improve-across-laps-with-a-safe-set ≈ our determinism + ~unlimited-attempts line-iteration loop (RL or classical).

**VALIDATES (already our plan, no change):**
- **acados + MPCC++** = our documented classical VQ2 alternative (tunnel/corridor constraints = the dynamic gate-weight idea). Standing caveats: acados-on-Windows is painful (build on Linux); RL is the *preferred* stretch (user-fit), this is the alt.
- **Agilicious / SWIFT (UZH-RPG)** = already our RL blueprint ("Architecture = SWIFT's"). Study the DR + transfer methodology; don't adopt the HW stack (we're setpoint-over-MAVLink).
- **Flightmare** = a reasonable alt RL surrogate, but Isaac Lab fits our **state→action** policy better (no rendering → orders-more parallel envs). Flightmare only matters if we ever do vision-in-the-loop RL (we don't).
- **NeuroBEM** = the BEM-nominal + NN-residual *pattern* validates our "model + learned residual" sim-to-sim step. The aero tool itself = physical-round only; in virtual quals the official sim's aero is ground truth we *measure* (system-ID), not model.

**REJECTED (clean pass — solves a problem we don't have):**
- **Ego-Planner-v2:** reactive gradient avoidance through *unknown cluttered* space; we have a *known deterministic* course + a pre-optimized line + no depth source. Opposite problem.
- **FastSAM:** we need 4 corner keypoints for PnP, not masks (segmenting → still must extract corners = extra compute for an unused representation). SAM-family niche for us = offline class-agnostic *obstacle* masks only (the triangulation flywheel).
- **GateNet:** "fisheye native" irrelevant (pinhole, no distortion); it optimizes DOWN for weak hardware while our plan sizes the detector UP into ~100 TOPS.
- **RT-DETR:** NMS-free latency-determinism is negligible at 1–2 gates/frame, and it's bbox not pose. Free A/B via ultralytics IF we ever *measure* NMS jitter as a problem (we won't).

**OFFLINE-LANE / "is between-runs processing a cheat?" — NO, it's our strategy:** record a run → optimize the line offline → race it next attempt is the determinism + ~unlimited-attempts plan; legal because nothing external is in the loop *during* the autonomous timed run (vision-in-loop tracks the precomputed line). It's the **latency-free lane** where heavy tools live (FastSAM, Depth-Anything, COLMAP/SfM, global trajectory opt; our offline obstacle-triangulation already here). The DISALLOWED version = *in-run* external compute or reading sim ground-truth state → controller. **Confirm submission/attempt mechanics at sim drop** — it decides the operational shape: live client (between-run offload trivial, your boxes) vs upload-a-sandboxed-artifact (offload baked into the artifact) vs they-run-your-code.

**CONTROLLER worry (user is an FPV pilot — "execution at speed is hard"):** well-founded but mitigated — we *lean on the sim's stabilizer* (not hand-flown acro), so the sharp edge is the stabilizer's **phase-lag + saturation at speed** = open-risk **R2**, measured by `innerloop_step` (delay/τ/overshoot, calibrates the placeholder thrust scale in [controller.py](src/racer/controller.py)). RL/MPCC later *learns/anticipates* that lag rather than fighting it — a concrete reason RL fits this worry. Do the system-ID first contact.

## Round 2 (2026-05-31) — a second list, after the helpers read our Round-1 decisions
Much better-targeted (clusters in our live lanes). Two through-lines: (1) most are heavy C++ (PVNet/rpg/GTSAM/Crocoddyl/SymForce) ⇒ Windows-build-pain (same as `toppra`) ⇒ Linux/offline tools or port-to-pure-Python; (2) several feed the RL twin's fidelity — disturbance observer + BA map covariance + system-ID = the measured noise/dynamics model the policy needs. Nothing is a "spike now"; all post-VQ1 queue or contingent.

- **PVNet (dense pixel-voting 6DoF pose) — PARK (measured-escalation for transit/occlusion).** Targets our real hard case (corners leaving frame at transit/bank) and dense voting IS genuinely better at truncation/occlusion than direct regression. But "YOLO-pose fails catastrophically" is oversold (ultralytics regresses off-image keypoint coords; we already flag low-conf → 3-corner P3P), a voted/extrapolated off-frame corner may not beat real 3-corner P3P, and it's a full re-tool off our committed YOLO-pose pipeline (locked corner order, synth data, adapter). Escalate IF first-contact recordings show the P3P fallback failing at transit — not before (vision = measure-before-escalating).
- **ADRC / Extended State Observer — QUEUE (the cleanest answer to the disturbance/residual gap; post-VQ1).** Lumps drag + thrust-scale error into one "total disturbance" state fed into the accel feedforward (fits [controller.py](src/racer/controller.py)'s accel→tilt+thrust), no plant model, <100 Hz. Caveats: it's an OUTER-loop observer around the sim's already-stabilized inner loop (value = what leaks through: thrust-scale drift + translational drag, not "all aero"); and RL subsumes it (learns disturbance rejection) ⇒ it serves the model-based safety-net track. Bonus: the ESO disturbance estimate is itself a first-contact MEASUREMENT of unmodeled dynamics → feeds system-ID + the RL dynamics-randomization range.
- **SymForce (symbolic Jacobian codegen, Skydio) — PARK (conditional + likely overkill).** Gated on hand-rolling an ESKF (our deferred fallback). Its sweet spot is on-manifold ORIENTATION Jacobians — exactly the part we engineered away (attitude given → linear KF). If the ESKF-bias fallback fires it's a small Python bias-state, not a manifold VIO; C++ codegen + Windows build is disproportionate. Remember it exists for that branch only.
- **rpg_trajectory_generation (min-snap, ETH/UZH) — VALIDATES the geometry rung; PORT, don't link.** Correctly identifies the missing step: TOPP-RA needs a geometric spline first, and `speed_profile.py` currently uses a placeholder cubic spline. Proper min-snap is the geometry rung (and it's the RPG/SWIFT lineage). But ROS/catkin C++ ⇒ Windows-pain; min-snap is a tractable QP we'd implement pure-numpy (like the speed_profile spike), using rpg as the reference. VQ2 quality upgrade (cubic-spline placeholder is fine for the floor).
- **GTSAM (factor-graph BA, Georgia Tech) — QUEUE (the offline mapper; layer-3 map-averaging; offline lane).** The principled "average sightings into a precise fixed map," and it emits per-gate marginal COVARIANCES → directly feeds [localization.py](src/racer/localization.py)'s `R` (well-constrained gates trusted more). Caveats: "sub-mm" oversold (bounded by PnP noise/observability); offline ⇒ runs on the Linux box/Adroit regardless of Windows; for our small deterministic problem (tens of gates, attitude given) a `scipy.optimize.least_squares` mapper may suffice (GTSAM = the robust upgrade). The first item I'd reach for when we build the mapper.
- **SKRL — VALIDATES (drop SB3 for an Isaac-native on-GPU RL lib); but evaluate rl_games / rsl_rl too.** Correct that SB3's numpy VecEnv bottlenecks at thousands of parallel envs. But the Isaac defaults are rl_games + rsl_rl; rsl_rl is the closest to the SWIFT/legged lineage + tightest Isaac Lab integration. So: Isaac-native not SB3; SKRL is one option, evaluate the others. (Minor: "Sequential Kinematics RL" is a made-up expansion — it's just "skrl".) Queue for the RL phase (post-VQ1).
- **Crocoddyl (DDP optimal control, LAAS) — INSPIRATION / classical alternative; NOT queued.** Same bucket as acados/MPCC (the model-based path we deprioritized for RL), and it additionally needs a DIFFERENTIABLE plant model — the classical-control work we route around. Would be the offline CPC/true-time-optimal rung if we ever go classical (Linux/offline OK). The ILC idea I liked does NOT require it: "iterate-across-laps" can be a model-free residual-feedforward loop on the tracker (measure lap tracking error → feed-forward-correct next lap) — lighter, exploits determinism. Take that cheap version.

**Net keepers:** ADRC (disturbance + a system-ID measurement) · GTSAM (offline mapper, cov→`R`) · min-snap via porting rpg (the geometry rung under TOPP-RA) · an Isaac-native RL lib (rsl_rl/rl_games/SKRL). PVNet + SymForce park contingent; Crocoddyl = the classical alt we're not taking (its ILC concept survives cheaply). Satisfying synthesis: ADRC's disturbance estimate + GTSAM's map covariance + system-ID all roll up into the measured noise/dynamics model the RL twin needs — even the classical-flavored picks serve the committed RL path.
