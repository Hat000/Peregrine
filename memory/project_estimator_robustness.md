**Problem (user's question, 2026-05-31):** motion blur + a slightly-inaccurate gate map make each gate-PnP world-position fix noisy/biased; feeding those to the KF risks jittery, unnecessary correction moves. How do we tell TRUE drift (correct) from NOISE (smooth away)? The user proposed a low-pass (random jitter cancels, consistent updates accumulate) + gating the fix by its agreement with the EKF prediction (a "dot product"). Both instincts are right and re-derive tools we already have on the board; the refinement below names them, fixes the math, and points out that the case actually worth fearing is one neither idea catches.

**The reframe that matters: zero-mean NOISE vs. BIAS.**
- A Kalman filter *is* the adaptive low-pass the user described — the Kalman gain `K = P Hᵀ (HPHᵀ+R)⁻¹` is small when `R` (fix noise) ≫ `P` (state confidence), so a noisy fix barely nudges the estimate and only *repeated* same-direction fixes accumulate. It optimally crushes ZERO-MEAN jitter. So the "darty corrections from random blur jitter" fear is largely already handled (given the two provisos below).
- The dangerous case is the OTHER thing the user named — "inaccurate gate positions" = a CONSISTENT BIAS. If a gate is mapped 0.3 m off, every fix against it pulls you 0.3 m the same way and the KF faithfully tracks it as real drift. **A low-pass does nothing here** (it passes a steady offset straight through). A plain low-pass is the right tool for the problem we don't really have and no help for the one we do — and you must NOT stack a 2nd low-pass on the KF (double-filters + lags the real corrections).

**The 3-layer scheme (what actually differentiates drift from noise/bias):**

1. **Adaptive `R` — BUILT; extend to motion-blur.** `R` already = PnP pixel-noise cov + attitude lever-arm term (range-dependent: 1° attitude err @20 m ≈ 0.35 m, dwarfs corner noise) + P3P 3-corner inflation (×9) — all in [localization.py](src/racer/localization.py) (`gate_pose_to_world_position` / `apply_gate_pose_update`). **EXTEND:** motion blur → higher `reproj_error_px` / lower `corner_confidence` (both already in our contracts) → inflate `R`. Strictly better than a blanket low-pass: it down-weights only the actually-bad frames, with no lag on the good ones. This is the layer that handles zero-mean noise.

2. **Mahalanobis innovation gating — DEFERRED to the navigator loop (the user's "dot-product-with-prediction", done right).** This is for OUTLIERS (wrong-gate association, teleport fixes, blur garbage), not smoothing — the KF still smooths what passes. Two fixes vs. the raw dot-product: (a) use the covariance-weighted innovation `d² = νᵀ S⁻¹ ν`, `ν = z − Hx̂`, `S = HPHᵀ + R` — NOT a position dot product, which rewards same-direction-AND-large-magnitude and would wave through a 2×-too-far over-shoot as "very consistent"; (b) threshold `d²` against a χ². Key self-adjusting property (answers "won't it reject corrections I need?"): after a long blind coast `P`→large ⇒ `S`→large ⇒ the gate WIDENS, so a legitimately-big correction still gets in; when confident it tightens. The gate breathes with uncertainty. Already flagged in the [localization.py](src/racer/localization.py) comment (NEG-3) + red-team pass-2 deferral; build it when wiring `Mission.run`'s navigator (needs live range-to-gate + the mapper).

3. **Map-averaging + multi-gate consistency + relative-at-transit — NOT built (the bias boss); determinism is the weapon.** (a) **Map averaging** — many sightings from many angles drive per-gate map error down (the mapper's job); feed the *residual* per-gate uncertainty into `R` so well-constrained gates are trusted more. (b) **Multi-gate joint PnP** — localize against all visible gates at once; a single biased gate gets outvoted AND its disagreement becomes observable (flag/down-weight). (c) **Relative control at transit** — when about to fly THROUGH a gate, close the loop on the gate you SEE (its image corners) for the centering DOF, not absolute world position; map error becomes irrelevant for the thing you physically must hit (what a pilot does). NB this is the sanctioned use of the directly-observed gate — distinct from the rejected full-IBVS-as-position-estimator.

**Control-side point — half of "unnecessary correction moves" is NOT estimation.** The loop already reads the KF's smoothed, forward-predicted state, never raw PnP fixes (the point of the predict/update split), so a noisy fix is a small gain-sized nudge the controller sees as a small smooth change, not a step. Track a smooth planned trajectory (min-snap line / TOPP-RA `speed_profile.py`) with bounded gains + velocity/accel feedforward ⇒ small estimate jitter → small DAMPED corrections, not darts. If we see twitchiness, the first knob is controller gains, not a new filter.

**Discipline — set thresholds from MEASURED noise, not guesses.** Every constant here (`R` scale, the χ² gate, the blur→`R` curve) should come from first-contact recordings: is the PnP error actually zero-mean, and how does it grow with range / blur / clipping? This is the SAME perception-noise-model flagged for the RL policy ([[project-tooling-recommendations-eval]]) — it pays for both the KF tuning and the RL observation model. Backstop where noise/bias is genuinely untamable: slow down — perception fidelity is the speed ceiling ("estimation = a speed cap with a safety valve").

**Status:** layer 1 BUILT (extend to blur — small add at the detector→localization seam) · layer 2 DEFERRED (navigator-loop wiring) · layer 3 NOT BUILT (needs the mapper). Related: [[project-master-plan]] (state_estimator component, NEG-3), [[project-red-team-pass-2]] (gating deferral), [[project-tooling-recommendations-eval]] (perception-noise-model).

## No-gate / blind-segment robustness — the "headless fly" problem (user concern, 2026-05-31)
**Concern:** what if NO gate is visible for a while — especially at lap START, or any inter-gate visibility gap? Our traversal-discovery design (Gate ordering, option C) assumes the next gate is findable from the current one, which is NOT guaranteed. Blind on gates ⇒ IMU-only x,y drift ⇒ risk of flying headless / missing the gate / leaving bounds. A REAL gap, not yet solved (distinct from the sub-1s gate-transit blink, which the IMU coast already covers).

**Conditions that could dissolve it (first-contact unknowns):** (1) sim emits position (`LOCAL_POSITION_NED`, R1) → no blind-gap problem at all (we capture it eagerly; `msg_audit` checks first); (2) rough gate map provided (R4) → fly toward the rough next-gate position, refine on sight; (3) VQ1 guidance aids (R3, "course guidance structures") → follow guide structures between gates (aids OFF in VQ2 ⇒ hardest there). **Worst case = no position + no map + aids off (≈ VQ2).**

**What already softens it:** baro pins z, mag pins yaw ⇒ even with zero gates only x,y drifts (4/6 DOF anchored); explore is SLOW by design (little ground per blind second); the KF coasts short gaps (<0.3 m/1 s). So "headless fly" is really "bounded x,y drift while altitude + heading hold."

**The real gap (doctrine exists, code doesn't):** master-plan Failure-handling says "gate-lost recovery = slow / hold / yaw-scan, never blind-throttle" — but `mission.py` has NO SEARCH state and `ReactivePlanner` assumes a target gate ⇒ "no gate visible" is currently UNDEFINED behavior. **FIX (navigator-wiring item; cheap; add REGARDLESS of the data):** an acquisition/SEARCH state — start the lap in it (don't assume gate 1 is in view post-takeoff); on no-gate-for-T, slow to hover/creep + **yaw-scan** (sweeps the 90° HFoV → finds any gate in the horizontal band) + an **altitude/pitch scan** for low gates (camera looks UP — 20° tilt, elev −9°..+49° ⇒ low gates hide below the band); resume forward only on reacquire; never blind-throttle.

**Feature-based correction (user idea) — the ONE case that genuinely re-opens "no VIO".** Our anti-VIO call was for the sub-1s gate-TRANSIT blink. A LONG no-gate stretch is different — IMU-only x,y drift grows unacceptably, and visual odometry WOULD bound it. **Right-size it (NOT full VIO):** attitude is GIVEN ⇒ we need visual TRANSLATION only. Lightest form — sparse features (`cv2` Shi-Tomasi + Lucas-Kanade PyrLK flow, cheap) → SUBTRACT the known rotational flow (we have attitude) → residual translational flow → a VELOCITY estimate → feed the KF's EXISTING velocity-update ⇒ drift grows LINEARLY not quadratically. The catch is SCALE (monocular up-to-scale): from baro-altitude + ground-plane (weak — camera looks up), known structure ranges, or the last gate's size as it leaves frame. The parked heavy VIO libs (OpenVINS/VINS-Fusion, [[project-tooling-recommendations-eval]]) are the fallback IF the light flow-velocity assist is insufficient — try light first. This bounds drift everywhere (RACE too) and tightens the RL perception-noise model.

**Sequencing — data-gate it:** instrument the first explore recording for inter-gate visibility gaps (how often / how long is NO gate in frame?). SEARCH state = add REGARDLESS (cheap insurance). Flow-velocity assist = DATA-GATED: VQ1-relevant IF gaps threaten explore COMPLETION (a validity issue, not just speed), else a VQ2 robustness upgrade. Overriding rule: when lost, slow/hold/search — never blind-throttle ("blind gap" must fail toward "stop and look," not "crash"; a slow VALID finish > a fast invalid one).
