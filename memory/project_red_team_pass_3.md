A 3rd third-party red-team report (3 blocks, ~17 claims) was triaged against the real code (line numbers had drifted again — verified by CONTENT). Same hit-rate pattern as passes #1/#2: a few real, several already-known, a few flat wrong. Branch `red-team-tier-a`, **169 tests green (was 159, +10)**, NOT yet merged to main, NOT yet committed (pass-3 edits in the working tree pending user OK).

**APPLIED — real fixes (each with a regression test):**
- **A2 — controller tilt-clamp vertical over-thrust (the strongest catch).** `controller._accel_to_attitude`: when the 45° tilt clamp fires, the code kept the FULL un-clamped thrust magnitude at the clamped angle, so a large horizontal demand (e.g. 3 g brake) put `|f|·cos45 ≈ 2.1 g` on the vertical axis → the drone rockets skyward on every hard turn/brake. Fix: altitude-priority — size the collective so its world-up projection equals the required vertical specific force (`f_mag = f_up / cos_tilt`); it's an identity when un-clamped, so the normal path is unchanged. Independent of the (still-placeholder) throttle calibration.
- **1.1 — mission gate-plane-crossing advance.** `Mission._passed` was a pure 1.0 m sphere; a fast fly-through (>0.5 m/frame) can clear the 1.5 m opening yet never sample inside it → `gate_index` sticks. Added: proximity OR (on/past the gate exit plane AND inside the inner square), through-axis oriented by the drone's VELOCITY (so it doesn't invert at the plane).
- **1.2 — planner U-turn on overshoot.** `ReactivePlanner` flipped the gate normal by `to_gate` (drone→gate), which inverts the instant the drone crosses the plane → carrot snaps to the approach side → high-speed U-turn back through the gate. Fix: disambiguate the normal sign by `nav.velocity_ned` when moving (falls back to `to_gate` at rest, preserving all existing tests). Pairs with 1.1 (which removes the trigger).
- **B3 — takeoff relative to start altitude.** `Mission` TAKEOFF targeted an ABSOLUTE `-takeoff_altitude_m`; if the baro isn't arming-zeroed (MSL bias), the pad isn't at z=0 → launches to the wrong height. Now captures the full start position (`_takeoff_xy`→`_takeoff_origin`) and climbs relative to it, mirroring how the start-xy was already captured. (Same root as the report's "3.1 baro sign flip", which was otherwise INVALID — the pz=-altitude contract + `atmosphere.pressure_to_altitude_m` already exist; the only real gap was the arming reference, = B3.)
- **A5 — localization attitude lever-arm covariance.** `gate_pose_to_world_position` propagated only PnP translation cov, treating attitude as exact (it documented this as a deferred refinement). A 1° attitude error at 20 m ≈ 0.35 m — dwarfs PnP cm-noise — so the KF over-trusted distant fixes and snapped z against the baro. Added `σθ²(|L|²I − LLᵀ)` (L = world lever arm; same skew/outer-product the predict step uses), `attitude_noise_std` default 1° (tunable at first contact, active by default so it isn't a dormant "documented but off" gap).
- **B2 — KF dt upper-clamp.** `predict` already no-op'd `dt<=0` (so the report's negative-dt "detonation" was ALREADY guarded — it hadn't read the code), but a forward sim-reset/stutter gives a huge POSITIVE dt. Added `max_dt_s=0.2` upper guard. Navigator still owns reset detection + re-init. This is the "clamp it" half of the deferred loop-gating note.
- **4.1 — sysid quadratic thrust-curve fitter.** `sysid.fit_thrust_curve` (quadratic + linearity ratio) so tomorrow's `innerloop_step` can DETECT rotor-curve nonlinearity (PWM→force is quadratic), not just fit a linear slope. Linear `fit_hover_thrust` stays as the seed. The controller's linear throttle map remains the documented R2 placeholder (no controller change — measure first).

**REJECTED — overstated/invalid (do NOT re-litigate; reasoning so we don't):**
- **A6 — "additive ambiguity-eps squashes real ratios; use `max(e1,1e-5)`."** WRONG, and directly contradicts the pass-#2 fix. The additive `AMBIGUITY_EPS_PX=0.1` is a NOISE-FLOOR soft-threshold: sub-0.1 px reproj differences are below detector noise (~1–2 px) and must NOT be treated as discriminative. The report's `e1=0.01 vs e2=0.08 = "8× unambiguous"` mistakes sub-noise numerical noise for signal. `max(e1,1e-5)` would re-introduce the exact frontal-gate coin-flip pass #2 fixed and would break `test_frontal_noise_free_ambiguity_ratio_is_finite`. (Two passes disagreed; the noise-floor argument settles it. EPS_PX is tunable to the measured detector noise at first contact — the only legitimate residual.)
- **B5 — "yaw-at-gate + sideslip pushes the gate out of FOV; blend yaw toward velocity."** Geometrically confused. The camera is BODY-FIXED; yawing the nose at the gate (current behaviour) CENTERS it regardless of sideslip. Sideslip changes velocity-vs-heading, not camera-vs-gate. The proposed "blend toward velocity" would point the camera AWAY from the gate during turns → worse. The real FOV risk is PITCH (= B1), not yaw.
- **A4 — IPPE prior "camera-relative death spiral" from ego-rotation.** Overstated. The two IPPE ambiguity solutions differ by tens of degrees; the per-frame ego-rotation (~2–3° at 33 ms) can't flip the binary tiebreak. Kernel of truth (disambiguate in the WORLD frame using the stable mapped gate orientation) is a minor future refinement (needs attitude plumbed into the camera-only gate_pose), not urgent.
- **A3 — "pure-pursuit crosses gates diagonally → hits the 260 mm frame; add centerline LOS."** Misread. The planner already places the carrot BEYOND the gate on its through-axis = a point on the extended centerline = exactly the LOS alignment the report recommends. Guaranteed-perpendicular passage is the RACE-mode (min-snap/MPCC) job, already planned.
- **1.3 — "IPPE no-prior path needs the P3P frontal heuristic."** Severity overstated (cheirality keeps BOTH IPPE solutions in front — it's a tilt error, not a 180° backward flip; and the planner uses the MAP orientation, not per-frame PnP). Fix is also RISKY: for a genuinely tilted gate in the ambiguous regime it would bias toward frontal (wrong). The drone POSITION fix is insensitive to the near-frontal tilt ambiguity (t_cam_gate ~equal), and the prior corrects subsequent frames. min-reproj is the principled no-prior choice. Not applied.

**DEFERRED / NOTED (already-known or unbuilt-wiring discipline — no code tonight, the night before the sim drop):**

- **2.1 + B4 + A1 — IMU-sample dropping / loop-dt / synchronous-vision deadlock.** All three are about the UNBUILT navigator loop, and the CORRECT architecture is already documented (free-running estimator at IMU rate, vision async, predict driven per-HIGHRES_IMU with dt from consecutive `time_usec` stamps — NOT the wall-loop period — and B2's clamp). The seam exists (`MavlinkClient.on_message` raw tap). Canonical wiring rule recorded; build the loop AT first contact with measured clock offsets (clock_probe), not blind tonight.
- **B1 — pitch-vs-FOV "blind on straights."** Real tradeoff, already documented (master-plan #6, "camera looks up"). Magnitude slightly overstated (at 40° nose-down the horizon is still ~9° inside the top edge; truly blind needs ~50°+ or gates above the horizon). A VQ2 racing-line constraint (bound pitch-down / treat gate visibility as a soft cost) + keep the blind-coast estimator robust.

The cheap monotonicity guard (drop a completed frame older than the highest yielded) is reasonable but belongs with the deferred delayed-vision ring buffer; not added tonight to avoid perturbing recorder semantics the night before contact.
